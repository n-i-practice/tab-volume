# tab-volume 1.0.0 提出候補の確認結果

## ZIP

- ファイル名は `tab-volume-1.0.0.zip`。スピーカーと音波のアイコンを反映した `7a58ba3` の `extension/` から作成した。
- SHA-256 は `8CCB840D02DAF0616FDF6F1D4D8704F97C576D5184942C9A5750D55F5EABB73A`。
- ZIP の直下に `manifest.json` があり、翻訳・アイコン・Ko-fi の画像を含む23ファイルを確認した。対応コミットと SHA-256 は ZIP と同名の JSON でも確認できる。

### 再作成とテスト

リポジトリのルートで `node --test` を実行する。テストには Node.js 22.7 以降を使う。

Python 3.10 以降で `python scripts/package_extension.py --ref HEAD` を実行すると、指定コミットの `extension/` だけを `dist/` に ZIP 化する。ZIP の隣の JSON にソースコミットと SHA-256 を記録する。保存先は `--output-dir` で変更できる。

## アイコンと掲載画像の確認

- 16 px のアイコンを明るい背景と暗い背景で表示し、スピーカーと2本の音波を確認した。128 px のストア用 PNG は絵柄が 96×96 px、四辺に16 pxの透明余白がある。ZIP ではマニフェストが参照する5サイズの PNG を照合した。 [アイコン原版](tab-volume-icon.svg) · [Chrome ウェブストアの画像要件](https://developer.chrome.com/docs/webstore/images#extension-icon)
- Windows の Chrome 157 で実際のポップアップを開き、70% の保存済みルールを表示して4言語の掲載画像を作り直した。掲載画像4枚は 1280×800 px、小型プロモ画像は 440×280 px で、いずれも RGB 8 bit。

## URL 変更時の回帰確認

- `node --test` の9件で、保存条件の照合とキーの互換性、キャプチャ開始時の URL 比較、連続した音量変更とリセットの処理順を確認した。
- 同じコミットを2回 ZIP 化し、SHA-256 が一致した。Windows の Chrome 157.0.8103.38 に展開して読み込み、フラグメントだけが変わった場合はキャプチャを開始し、クエリが変わった場合は開始を取り消すことを確認した。スライダーとリセットボタンの動作、保存・適用・削除も確認した。

## 更新版 ZIP の再確認

`5b6e24a` の提出用 ZIP を Windows の Chrome 157.0.8103.38 に読み込んだ。W3C の公開デモで **Sintel teaser** が再生され、50% への調整、ミュートと解除、ホスト条件の保存、別タブでの適用、100% に戻す操作、設定一覧からの削除まで通った。 [審査用の操作手順](REVIEW.md#test-instructions)

4言語のキーボード操作と、旧版からの言語・音量設定の移行3ケースも同じ ZIP で再確認した。ZIP の全22ファイルを `extension/` と照合し、掲載画像4枚と小型プロモ画像のサイズ・色形式を再確認した。

## 確認できたこと

Windows の Chrome 157.0.8103.38 の一時プロファイルで確認した。

- 未調整タブでポップアップを開くと 100% が表示され、キャプチャは開始されない。音量変更で開始し、ミュートと解除が反映される。
- ホスト、パス、選択したクエリパラメータの3種類を保存できる。保存値を手動で適用でき、削除した行は一覧から消える。
- 同一オリジン内で再読み込みなしに URL を変えると、ポップアップの照合結果が更新される。調整中の音量は URL 変更だけでは変わらない。
- 別タブは 100% から始まる。ブラウザーを終了して同じプロファイルで開き直すと、音量ルール、言語、ダークモード、目盛りが残り、保存値を再度適用できる。
- ポップアップを日本語、英語、ヒンディー語、簡体字中国語に切り替えて表示した。掲載用 PNG は各 1280×800、小型プロモ画像は 440×280。いずれも RGB 8 bit。
- Ko-fi ボタンは画像抽出拡張と同じ URL を使っている。外部からの自動確認には HTTP 403 が返ったが、利用者のブラウザーでは支援ページが正常に開いた。

## Chrome 116 の確認結果

Windows の Chrome for Testing 116.0.5845.96 の一時プロファイルで、提出用 ZIP を展開して読み込んだ。`chrome://extensions/shortcuts` で tab-volume を開くショートカットを割り当てた。ツールバーのアイコンのクリックは、ウィンドウ操作時に `window id … no longer belongs to Chrome; current owner is Chrome` が返ったため未確認。

1. ローカルのテスト音を再生し、ショートカットでポップアップを開いた。初期値は 100% で、キャプチャは開始されていなかった。
2. 50% に下げるとキャプチャが開始された。ゲイン適用後のテスト音の振幅は 100% 時の約半分だった。ホスト単位で 50% を保存した。
3. 同じホストの別タブを開くと初期値は 100% だった。「適用」でキャプチャが開始され、50% になった。

## 既存インストールからの更新

Windows の Chrome 157.0.8103.38 の一時プロファイルで旧版 `50737a8` を読み込んだ。旧版の保存形式で、ホスト単位の 70%、ダークモード、細かい目盛りと言語を設定した。同じフォルダーに提出用 ZIP を展開して拡張を再読み込みした。

- 日本語の Chrome で、手動選択したヒンディー語は保持された。「自動」は日本語に変わった。
- フランス語の Chrome で、「自動」は英語に変わった。
- 3ケースとも、音量設定・ダークモード・目盛りの保存値が残り、設定一覧に 70% のルールが表示された。

## 4言語の表示とキーボード操作

Windows の Chrome 157.0.8103.38 で提出用 ZIP を読み込み、日本語、英語、ヒンディー語、簡体字中国語それぞれの一時プロファイルで同じ手順を実行した。

1. 各言語でポップアップの初期選択を確認した。Tab で歯車を選び、Enter で開いて Space でダークモードをオンにした。色の切り替えはポップアップ内で反映された。
2. Tab でスライダーに移り、矢印キーで 100% から 90% に変更した。200% の目盛りラベルを Enter で選び、Space と Enter でミュートと解除を行った。ミュート中も表示は 200% のままで、スライダーは無効になった。
3. 矢印キーと Space で保存単位とクエリパラメータを選び、Enter で 200% を保存した。100% に戻してからキーボードで適用し、200% への変更と読み上げ用の通知を確認した。
4. キーボードで設定一覧を別タブに開き、同じ言語で表示されることと、Enter で保存項目を削除できることを確認した。長い URL はポップアップのアドレス、ポップアップの保存済み条件、設定一覧の条件のいずれでも横にはみ出さず折り返した。

## 通常再生と拡張経由の 100% の比較

Windows で提出用 ZIP を読み込み、Chrome 157.0.8103.38 と Chrome for Testing 116.0.5845.96 で各3回計測した。左右別の周波数（733 Hz と 997 Hz）を流し、1秒ごとに映像の点滅と音声のレベル変化が同期するステレオ WebM を使った。

1. 通常経路で動画を再生し、途中で 90% に変更してキャプチャを開始した。続けて 100% に戻し、同じ動画を拡張経由で再生した。
2. テスト用 Chrome のプロセスだけを対象に Windows のループバックで出力を取得した。10 ms 区間の実効値で音量と音切れを比較し、映像の表示予定時刻と音声レベルが上がった時刻を照合した。 [Windows のプロセス別ループバック](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/)

| 項目 | 結果 |
| --- | --- |
| 切り替え直後 | ほぼ無音の区間が Chrome 157 で約 110 ms、Chrome 116 で約 110〜120 ms 続いた。 |
| 安定後の音声 | 両バージョンで通常経路に対する実効値の差は左右とも 0.03 dB 未満だった。左右のテスト音は分離したままで、基本周波数以外の成分の割合に目立つ変化はなく、追加の音切れも検出しなかった。 |
| 安定後の映像同期 | Chrome 157 では通常経路より音声が約 75〜85 ms 遅れた。Chrome 116 は映像フレームの時刻を十分に取得できず、同期の判定は保留した。 |

計測にはテスト信号とブラウザーが報告する映像時刻を使った。実際の動画での利用者の聴き比べは後述する。出力機器ごとの比較と Windows 以外の OS は未確認。

### 遅延の切り分け

Windows の Chrome 157.0.8103.38 で、同じステレオ動画を使って再計測した。提出用 ZIP の一時コピーで `AudioContext` の設定やゲインの接続だけを変え、同じ試行内の通常再生を基準に、キャプチャ経由の 100% で増えた音声の遅れを比較した。

| 条件 | 回数 | `baseLatency` | 通常再生から増えた遅れ |
| --- | ---: | ---: | ---: |
| 現行の `new AudioContext()` | 3 | 10 ms | 約 81〜85 ms |
| `latencyHint: 0` | 3 | 10 ms | 約 77〜89 ms |
| `GainNode` を経由せず Web Audio の出力に直結 | 3 | 10 ms | 約 80〜83 ms |
| `latencyHint: 'playback'`（検出用の対照） | 1 | 20 ms | 約 104 ms |

Chrome のトレースでは、タブ音声取り込みの内部遅延が 20 ms、Web Audio への受け渡し時の待ち時間が安定区間で約 9〜21 ms だった。この環境では出力バッファの最小値は 480 フレーム（48 kHz で 10 ms）だった。ブラウザー内の各値は異なる区間を測っており、表の遅れは映像との比較から求めた。既定の `interactive` と `latencyHint: 0` は同じ出力バッファになり、ゲインを外しても遅れは残った。 [Chromium の取り込みバッファ](https://github.com/chromium/chromium/blob/157.0.8103.38/services/audio/loopback_signal_provider.cc#L47-L70) · [Web Audio の遅延設定](https://www.w3.org/TR/webaudio-1.0/#dom-audiocontextoptions-latencyhint)

別の1試行で、100% の再生中にトラックを停止して通常経路へ戻した。映像に対する音声の遅れは通常再生の約 33 ms からキャプチャ中は約 110 ms になり、停止後は約 35 ms に戻った。戻す際に約 20 ms のほぼ無音の区間があった。

同じ Chrome と動画を使った比較では、参考拡張の Volume Master 2.4.0 でも 100% に戻した後に約 75〜85 ms の追加遅延があった。 [参考拡張との比較](../reference-tab-volume.md#100-に戻した後の音声の遅れ)

## 「100% に戻す」ボタンの確認

- Windows の Chrome 157.0.8103.38 と Chrome for Testing 116.0.5845.96 で更新版を確認した。スライダー、数値ラベル、保存済み設定の適用で 100% にすると、同じストリームが続いた。「100% に戻す」ボタンを押すと音声トラックが終了し、`AudioContext` が閉じた。
- 未調整時、拡張でミュート中、キャプチャ開始処理中のリセットを確認した。リセット後は 100%・ミュート解除になり、ポップアップを開き直しても未調整だった。続けて別の音量を選ぶと再キャプチャできた。
- 更新版 ZIP を Chrome 157 に読み込み、通常再生 → スライダーで 100% にしたキャプチャ経由 → ボタンで戻した通常再生の順に、同じテスト動画で3回測定した。スライダーで 100% にした状態は通常再生より約 79〜85 ms 遅れ、ボタンを押すと通常再生時の測定値との差が 2 ms 以内になった。切り替え時に約 12〜20 ms のほぼ無音の区間があった。

## 公開動画での同期計測と聴き比べ

更新版 ZIP と Windows の Chrome 157.0.8103.38 で、W3C の **Sintel teaser** の WebM を再生した。通常再生、スライダーで 100% にしたキャプチャ中、ボタンで通常再生に戻した後を、同じ動画の冒頭から各12秒計測した。4区間の波形を照合すると、キャプチャ中は映像に対して通常再生より約 75 ms 遅れ、ボタンで戻した後の差は約 1.5 ms だった。 [W3C の公開サンプル](https://www.w3.org/2010/05/video/mediaevents.html)

利用者による簡易測定では、音量変更前は約 100 ms、音量変更後は約 150 ms と表示された。音が聞こえた時点でキーやボタンを押す方式なので、約 50 ms の差には入力タイミングのばらつきも含まれ得る。映像同期の計測値とは分けて記録する。 [イヤホン遅延簡易チェッカー](https://lucycal.net/web_tool/SoundDelayChecker/SoundDelayChecker.html)

利用者が点滅とビープ音を合わせる同期テストを実施したところ、通常再生では約 70 ms、音量調整中は約 120 ms だった。「100% に戻す」ボタンでは通常再生と同程度に戻り、スライダーで 100% にしても遅れが残った。数値は利用者が音と点滅を合わせた目安。 [AudioTest の同期テスト](https://audiotest.io/audio-latency-test/)

利用者が実際の動画で聴き比べたところ、視聴時に遅れは気にならない程度だった。Windows 以外の OS での視聴確認は残っている。

1. 更新版 ZIP を展開して Chrome に読み込む。普段見る会話動画、または W3C の **Sintel teaser** を再生する。動画プレーヤー側の音量は一定にする。
2. tab-volume で一度 70% に下げ、スライダーで 100% に戻す。口元や打撃音のタイミングが分かる場面を見る。
3. 「100% に戻す」ボタンを押して同じ場面を再生する。映像と音のずれ、歪み、途切れを比べ、ボタンを押した直後の一時的な音切れは分けて記録する。

## Chrome 116 の手動確認

1. Chrome for Testing 116.0.5845.96 を、普段の Chrome とは別の `--user-data-dir` で起動する。`chrome://version` でバージョンが 116 であることを確認する。 [Chrome for Testing](https://github.com/GoogleChromeLabs/chrome-for-testing)
2. `chrome://extensions` でデベロッパーモードをオンにし、提出用 ZIP を展開した `manifest.json` のあるフォルダーを読み込む。パズルアイコンから tab-volume をピン留めする。 [展開した拡張機能の読み込み](https://developer.chrome.com/docs/extensions/get-started/tutorial/hello-world#load-unpacked)
3. [W3C のテスト動画](https://www.w3.org/2010/05/video/mediaevents.html) を開き、動画の音が出る状態にする。ツールバーの tab-volume をクリックし、表示が 100% であることを確認してから 50% に下げる。音が小さくなればキャプチャ開始は成功。
4. 「音量設定を保存」を開き、保存単位を「ホスト」にして保存する。同じ動画を別タブで再生し、初期値が 100% であることと、「適用」を押すと 50% に変わることを確認する。
